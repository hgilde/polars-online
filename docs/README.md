# The documents, and which to read for what

The README is the user guide. The API reference, built from the docstrings,
is at <https://hgilde.github.io/polars-online/>. Everything under `docs/`
falls into one of two kinds: a **guide** you read to do something, or a
**record** of how a decision was reached, kept because the code cites it.
Records are not rewritten when the code moves on; their status line says
what happened next.

## Guides

| document | read it when |
|---|---|
| [STATE-WORKFLOW.md](STATE-WORKFLOW.md) | you save a bank from a query, serve from it, or resume it — what each step guarantees, and the measurements those guarantees rest on |
| [PERFORMANCE.md](PERFORMANCE.md) | something is slower or bigger than you expected — where the time and memory go, every measurement, and the knobs that move them |
| [REGIMES.md](REGIMES.md) | you are about to trust `deco`, `rcov`, `hmm`, `corrchange` or `bocpd` — what each finds on data whose truth is known, and what it misses |
| [OUTPUTS.md](OUTPUTS.md) | you want to know what a model writes into its column — every field of every model, generated from the code and checked against it |
| [VALIDATION.md](VALIDATION.md) | you wonder where a default came from — generated by `scripts/validate.py` on public data; never edited by hand |
| [TESTING.md](TESTING.md) | you want to know what the suite proves, what it has found, and where it is thin |
| [EXTENDING.md](EXTENDING.md) | you are adding a model — every layer it touches, with the test that catches skipping each one |
| [RELEASE-READINESS.md](RELEASE-READINESS.md) | you are cutting a release, or asking which Polars versions are promised and which are merely measured |

## Records

| document | what it decided |
|---|---|
| [PLAN.md](PLAN.md) | the design and the task list — the source of truth. §1–§10 are the original design, §11 the task list with every task ticked, §11a the decisions taken while building, §11b–§11h one summary per follow-on document below, §12 the questions the design left open and their answers |
| [ENHANCEMENTS.md](ENHANCEMENTS.md) | every model and feature after the first seven (E1–E64): what was proposed, what was measured, what was built and what was declined |
| [CLUSTERING.md](CLUSTERING.md) | the survey behind `kmeans` and `micro` — every clustering family, decided against the library's contract, the two that passed and why the rest did not |
| [ANSWERS-E54-E64.md](ANSWERS-E54-E64.md) | the formulae and constants for the correlation and regime models, read from the papers before they were built |
| [REVIEW-E54-E64.md](REVIEW-E54-E64.md) | the code review of tasks 45–56: 29 items, all resolved in task 57 |
| [IMPROVEMENTS.md](IMPROVEMENTS.md) | the pre-release review by axis — correctness, performance, usability, extensibility, testing — with the decision on each item |
| [SIMPLIFICATION.md](SIMPLIFICATION.md) | what complexity was removed after the performance work, and what was kept on purpose |
| [BEYOND-O-STATE.md](BEYOND-O-STATE.md) | what relaxing the O(state) rule to O(window) would unlock — a survey; three of its six candidates were since built inside the rule (conformal intervals, `ew_cov` lags, `label_delay`) |
| [BOOSTED-TREES.md](BOOSTED-TREES.md) | how far gradient-boosted trees can be pushed toward the library's contract — a numpy prototype, measured, nothing in Rust |

Three more documents live at the top of the repository: `CHANGELOG.md`, one
entry per release with what changed and why; `CONTRIBUTING.md`, the gate and
the commit conventions; and `llms.txt`, the map a coding agent reads before
it writes against this library.

The code cites these by section number (`docs/PERFORMANCE.md §11`,
`docs/PLAN.md §4.4`, `E56`, `C5`), so sections keep their numbers even where
the order inside a file has been tidied.
