## Patterns

Four findings recur across models. A fix should land in every instance,
and a test written for one should be run against the others.

- **A. A live accumulator read inside a windowed path.** The windowed
  view is built and then one read goes to `self.…` instead: `ewridge`'s
  standardized solve (C1), `ew_class`'s `full`-shape factor (C12). Grep
  for `self.cov`, `self.classes` inside any function that has a `view`
  in scope.
- **B. Centring without an intercept.** With `standardize` on and
  `add_intercept = false`, `lasso` (C8), `kalman` (C10) and `robust`
  (C11) centre the features anyway; `ewridge` alone scales by the raw
  second moment. `sgd`'s `scale_features` is the next place to look.
- **C. A zero-weight row treated differently from a null target.**
  `lasso`'s selection has no `0/0` guard (C7); `kalman` (S9) and `robust`
  (S13) decay the per-target residual weight on a null target but not on
  a zero weight. `ewridge` gets both right and is the reference.
- **D. Which `n_eff` a windowed model reports.** `ewridge` reports the
  in-window weight; `lasso` (C9) and `ew_class` (S14) report the whole
  history while fitting on the window. One rule is needed, and hard rule
  8 should say which.

## Findings

Prefix: **C** changes a number or a state; **S** a semantic inconsistency
between two places that both look intentional; **P** performance against
a stated invariant; **D** documentation; **V** something a pass could not
confirm and the next one should.

### C1. `solve_standardized` reads the live accumulators under a `window`

`crates/online-core/src/ewridge.rs`, `solve_standardized`, the
`add_intercept` branch. Pattern A.

`solve()` passes the truncated `cov` it got from `view()`, and the
no-intercept branch reads it. The intercept branch reads `self.cov`:

```rust
let means: Vec<f64> = zidx.iter().map(|&z| self.cov.mean(z)).collect();
...
c[i * kf + j] = self.cov.cov(zidx[i + 1], zidx[j + 1]);
```

while `keep` in the same branch reads `cov.raw(...)`. So with `window` +
`standardize` + `add_intercept` the centred Gram and the means are the
**full** history and the right-hand side (`b`, `ybar`) is the windowed
one. The coefficients come from two different histories and the window's
guarantee -- no row older than the window reaches the fit -- fails
silently. The comment above the line ("Materialized up front: the solve
below borrows `self` mutably") is stale.

Fix: `cov.mean(z)`, `cov.cov(..)`. Test: run
`a_windowed_fit_is_the_fit_of_the_rows_inside_the_window` with
`standardize = true`; it should fail today. Until fixed, `validate` should
refuse `window` with `standardize`, the way it refuses `window` with
`ridge_decay`.

### C2. `view()` falls back to the live state when the window is empty

`crates/online-core/src/ewridge.rs`, `view`, `n_eff`, `sigma2`, `solve`;
**the same code in `lasso.rs`** (`Lasso::view`, `?` on `truncated_mean`).

`view()` uses `?` on `truncated(..)` and on `truncated_mean(..)` for every
target. Both return `None` when the in-window weight is `<= 0`. `view()`
turns that into `None`, and every caller treats `None` as "nothing has aged
out yet, read the live state" -- the same value the early return for
`old.cov.w == 0.0` gives. The two situations are opposites.

When it happens:

- a target that was null on every row inside the window -- a sparse
  long-horizon label beside a dense one -- makes the whole view `None`, so
  **every** target is solved on the unwindowed Gram and `n_eff` reports the
  unwindowed weight (so `min_periods` passes). It flips back when the
  target reappears;
- a clock gap at or beyond the window;
- a tiny negative from rounding in `w_now - f * old.w`.

`window.rs`'s `trim` comment says the model "reports an empty window rather
than stale numbers"; `ewridge` does the reverse. Note also that
`predict` gates a slot on the *untruncated* `self.wj[j] > 0.0`, and that
`step`'s first-solve clause reads `self.cov.n_eff()` (untruncated) where
`predict` reads `self.n_eff()` (truncated).

**`ew_class::view` is the model to copy**: a class whose `truncated`
comes back `None` is replaced by an empty accumulator ("scores nothing
rather than scoring on rows the window excludes") and the view is still
returned.

Fix: make `view()` return a three-way answer (live / truncated / empty),
handle the empty case per target (that target's slots NaN, its `r`
untouched) rather than for the model, and clamp the truncated weight at 0
before the test. Tests: a two-target windowed fit where target 1 is null
for longer than the window -- target 0's coefficients must not move when
target 1 goes null, and `n_eff` must not jump. Same test on `lasso`.

### C3. A `session_shrink` blend never re-solves

`crates/online-core/src/ewridge.rs`, `blend_toward_long_run`, `step`;
`crates/online-polars/src/stream.rs`, `run_instance`, `predict_chunk`.

`blend_toward_long_run` mixes `cov`, `wj`, `r` and `tm` and leaves `beta`
as it was. `step`'s `due` test has no "blended since the last solve"
clause. With the bank's defaults (`solve_every = halflife / 50`,
`max_rows_between_solves = u32::MAX`) the first rows of a new session are
predicted with the pre-blend coefficients; the blend reaches `pred` only
when the schedule next fires. The point of the feature -- "begin the day
partway back toward the long run" -- is missed on exactly the rows it is
for. The test helper `coefficients_after_blend` documents the staleness
("after a blend the coefficients are stale until the next solve") but
nothing in the stream forces the solve.

`predict_chunk`'s "blended" class is affected the same way: it blends a
*copy* and calls `predict`, which reads the copy's untouched `beta`, so it
writes the same `pred` as the as-is class (only `n_eff` differs). Its
docstring promises the row "is scored by a blended copy".

Fix: `blend_toward_long_run` sets a `stale_beta` flag (or calls `solve()`
when `beta.is_some()`); `due` includes it; `predict_chunk` blends then
solves on the copy. Test: `session_shrink = 1.0`, one row after the
boundary, `pred` equals the slow twin's own fit.

### C4. Building a `predict` plan drains the caller's closed-group queue

`python/polars_online/_frame.py`, `_source`.

```python
bank = make_bank()
schema = step(bank, pl.DataFrame(schema=in_schema)).schema
...
closed_schema = bank.closed_groups()
```

`closed_groups()` defaults to `drop=True` (`_polars_online.pyi`). For
`lf.online.predict(bank)` with a `ModelBank`, `make_bank` is `own()`,
which returns the caller's live bank, so building the plan discards every
closed row the caller has fitted and not yet read. `predict` is documented
as leaving the bank untouched.

Fix: `bank.closed_groups(drop=False).clear()` (or a schema-only accessor
on the native side). `DataFrameOnlineNamespace.fit_predict` also calls
`closed_groups()` twice in one expression -- the first drains, the second
supplies the schema -- which is correct only by Python's left-to-right
argument evaluation; take the frame once and use `.clear()` for the schema.

### C5. `label_delay` ignores a reset or session boundary on a skipped row

`crates/online-polars/src/stream.rs`, `apply_label_delay`.

The `!plan.accept` branch pushes the plan through and returns without
touching `self.pending`. `run_instance` still applies `reset`, `blend` and
`clear_lags` for that plan, because those run before its `accept` test.
So:

- **reset on a skipped row**: the models restart, `pending` survives, and
  the previous session's rows are replayed into the fresh model;
- **session change or capped gap on a skipped row**: the lag ring is
  cleared at the skipped row, and the rows still waiting from before it
  are released afterwards -- paired across the very break the clear was
  for. This is the L2 failure the comment in the accepted branch
  describes, reached by the other door.

Fix: in the skipped branch, `if plan.reset { self.pending.clear() }` and
`if plan.session_changed || plan.capped { release everything before the
plan }`. Test: `label_delay` with a session change on a feature-null row.

### C6. `ridge_decay` + `session_shrink` resets `prior_scale` at every blend

`crates/online-core/src/ewridge.rs`, `blend_toward_long_run`. **Confirmed
in pass 2** (was V1): `EwCov::set_moments(mean, centered, w_sum, q_sum)`
takes no `prior_scale`, and `prior_scale` moves only in `EwCov::update`
(`self.prior_scale *= lam`).

The blend builds `let mut blended = EwCov::new(k)` and fills it with
`set_moments(..)`, so the new accumulator carries a fresh `prior_scale`
and the decaying prior -- "the product of every decay factor the stream
has applied" -- is restored to full strength on every session boundary.
`validate` allows the combination while refusing `window` + `ridge_decay`
for the analogous reason.

Fix: carry `prior_scale` through the blend (the fast side's, or the same
mixture as the weights), or refuse the pair. Test: `ridge_decay` +
`session_shrink = 0` (a no-op blend) must leave the next solve bit-identical
to no blend at all.

### C7. A zero-weight row after warm-up poisons the lasso's lambda selection

`crates/online-core/src/lasso.rs`, `step`, the selection block. Pattern C.

```rust
let w_new = sel_lam * self.sel_w[j] + weight;
let a = sel_lam * self.sel_w[j] / w_new;
```

with `sel_w[j] == 0` and `weight == 0` is `0/0`. `sel_w` first moves on
the first row whose `pred` is finite; if that row carries weight 0 --
`min_periods = 1`, row 2 with `w = 0`, which hard rule 9 says is legal --
every `sel_err[j][li]` becomes NaN and stays NaN: `err[li] < err[best]`
is then false for every `li`, `sel_idx` sits at 0 (the largest penalty)
and `lam_selected` never moves again. `EwRidge::step` guards the same
recursion with `lam * wj + weight > 0.0`; this block does not.

Fix: the same guard. Test: warm up, one zero-weight row, then more rows;
`lam_selected` must still change.

### C8. Lasso without an intercept solves a centred/uncentred hybrid

`crates/online-core/src/lasso.rs`, `standardized`. Pattern B.

`C` is built from `acc.cov(..)` (centred co-moments) and `s` from centred
variances for every slot, regardless of `add_intercept`. With
`add_intercept = false`, `ybar = 0`, so `d_i = r_i / s_i` is the *raw*
cross-moment, and no intercept is recovered. The KKT system solved is
neither the centred problem (which would need `ybar` and an intercept)
nor the raw one (`E[xx']`, `E[xy]`); its solution is OLS only when the
features have zero mean. `EwRidge::solve_standardized`'s no-intercept
branch uses raw second moments for exactly this reason ("there is no
centering here, so no cancellation either"). Every lasso test uses
`add_intercept = true`.

Fix: without an intercept, scale by `sqrt(raw(i,i))` and drop the mean.
Test: `zero_penalty_matches_ols` with `add_intercept = false` and
features offset by a constant.

### C9. `Lasso::predict` reports the unwindowed `n_eff`

`crates/online-core/src/lasso.rs`, `predict`. Pattern D. `n_eff` there is
`self.cov.n_eff()`, the full-history weight; `Lasso::n_eff()` (windowed)
exists and is what `EwRidge::predict` uses. Under a `window` a lasso's
`n_eff` field and its `min_periods` gate are on the whole history while
its fit and `lam_selected` are on the window, and the two models disagree
on what `n_eff` means under the same option. Use `self.n_eff()` (after
C2 is fixed, or the fallback makes it worse).

### C10. Kalman standardizes without an intercept by centring anyway

`crates/online-core/src/kalman.rs`, `scales_into`, `standardized`,
`coefficients`. Pattern B. With `standardize = true` (the default) and
`add_intercept = false`, `off = 0` and every slot is `(x_i - m_i) / s_i`.
The filter's prediction is `Σ b_i (x_i - m_i)/s_i`, which carries a hidden
intercept `-Σ b_i m_i / s_i`; `coefficients()` returns `b_i / s_i` and has
no slot for it, so `coef · x != pred`. `EwRidge` avoids centring in its
no-intercept path. The `river` cross-check test turns `standardize` off,
so nothing pins this.

Fix: without an intercept, scale only (`x_i / s_i` with `s` from the raw
second moment), or document that `coef` does not reproduce `pred` there.
Test: `add_intercept = false`, features with non-zero mean, assert
`dot(coef, x)` against the step's `pred`.

### C11. Robust standardizes without an intercept by centring anyway

`crates/online-core/src/robust.rs`, `solve_standardized`. Pattern B;
**confirmed in pass 3** (was V6). With `off = 0`: `c` is the centred
co-moment matrix, `s` the centred standard deviations, `ybar = 0` so
`bsub[i] = b[i] / s[i]` is the raw cross-moment, and no intercept is
recovered -- C8's hybrid system exactly, with the same fix (the raw
second-moment scaling `EwRidge` uses). Every robust test uses
`add_intercept = true`, and the comment "Same scheme as
EwRidge::solve_standardized" is true only of the intercept branch.

### C12. `ew_class`'s `full` shape factorizes the live covariance under a `window`

`crates/online-core/src/ewclass.rs`, `score`, the `Covariance::Full` arm.
Pattern A.

`score` builds `view()` and reads the class means and weights from it,
but the factor comes from `self.class_matrix(c)`, which reads
`self.classes[c].comoments()` -- the untruncated moments. So under a
`window` the `full` shape's quadratic form and log-determinant are those
of the whole history, applied to a `delta` measured from the windowed
mean. `shared` reads `classes[c].comoments()` (the view) and `diagonal`
reads `cov.var(i)` (the view), so only `full` is wrong. The window's own
doc says its cost is "one `O(k^3)` factorization per class per row"
because "a window's truncated covariance moves every row" -- that
factorization is paid every row (`invalidate_all`) to factorize the wrong
matrix.

Fix: `class_matrix` takes the accumulator to read (`&classes[c]`), and the
cache is keyed off it. Test: `every_shape_matches_the_from_scratch_oracle`
with a `window`, or simply `full` vs `shared` under a window on the
identical-twin stream of `shared_equals_full_when_the_classes_share_
their_moments` -- they must still agree.

### S1. `sigma` and `resid_z` are not windowed at the bank level

`ewridge.rs` `sigma2` doc: "Under a `window` this is the variance *inside*
it, so `sigma` and `resid_z` describe the same rows the fit does"; and
`RidgeMoments` carries `wsig` / `sig2` for that. But the bank's `sigma`
field is `Stream::resid_var` (`stream.rs`, `run_instance`), an unwindowed
EW mean per slot on the instance's decay; `EwRidge::sigma2` is never read
by the stream. So a windowed spec reports a windowed fit beside an
unwindowed spread -- the outcome the model's own comment says it exists to
prevent. Either route the model's `sigma2` through for windowed specs or
correct the docstring.

### S2. Per-target `min_periods` gates on the shared `n_eff`

`stream.rs`, `step_n_eff_below`. Each target's threshold is compared with
the model's single `n_eff` -- the feature-side weight, which hard rule 8
defines and which is the same for every target. A target that is null on
most rows passes warm-up on the strength of the feature count, not its
own evidence (`EwRidge::target_weights` has the per-target number). This
is consistent with rule 8 and not with what "per-target warm-up" (E7)
suggests. Decide which is meant and document it; if the latter, the trait
needs a per-target weight.

### S3. Skipped-row time is folded without the cap

`clock.rs`, `advance`. Each row's delta is clamped at `max_dclock`, and a
skipped row's clamped delta is added to `pending`; the next accepted row
receives `pending + d`, which can be `n × max_dclock` after `n` skipped
rows. `max_dclock` is documented as a ceiling on the delta a model sees
("a weekend does not decay the state to nothing") and that holds per row,
not for the folded total. Probably the cap belongs on the total as well.

### S4. Two `ModelState` variants share the kind string `"ew_cov"`

`model.rs`, `kind()`: `EwCov` and `EwCovModel` both answer `"ew_cov"`. A
`WrongModel { found: "ew_cov" }` cannot say which, and
`AnyModel::restore`'s error for the bare accumulator reads "expected a
bank-supported model, found ew_cov" -- but `ew_cov` is a bank-supported
model. Give the bare accumulator its own kind.

### S5. A single-combo `ew_ridge` loses its combo metadata

`stream.rs`, `combos`: with one ridge and one feature set it returns
`Combo::default()` (`ridge: None`), while a grid carries `ridge:
Some(r)` and `feature_set`. The struct exists "so metadata can never drift
from the string"; a reader of the metadata for the single-combo case gets
nothing. Fill the values whatever the count; only `label` should be empty.

### S6. `window.rs` disagrees with itself on the boundary row

Module doc: a snapshot taken before the row at `t_j` carries everything
strictly older than `t_j`, so subtracting it retains `t_j`. `truncated`'s
doc: "everything at or before the snapshot's clock removed". `trim`'s
comment on a single stale entry: "it will subtract the whole accumulator"
-- it subtracts the state *before* the last learned row, so that row
stays in. The module doc is the correct one. Also: `trim` has an `if`
whose body is only a comment, and `new` applies `every.max(1)` after
already refusing `every == 0`.

### S7. `EwRidgeCfg::validate` gaps

Pass 2 (V2): `Spec::validate` refuses a repeated value in a grid
(`first_duplicate`, "ridge lists {} more than once") and a feature set
that names an unknown feature. Not found at either layer: feature-set
names unique (duplicates give duplicate output labels -- `deco` refuses
the same for its blocks in `stream.rs`); a column repeated within a set
(a repeated index duplicates a row and column of the sub-Gram, which is
then rescued by the jitter ladder and counted as a failure instead of
refused); `ridge` values finite and `>= 0`; `min_periods >= 0`; the decay
(`halflife > 0`, `lam` in `(0, 1]`). Whichever layer owns them, the
model's own `new` should not accept a config that cannot be solved.

### S8. `AnyModel::solve_failures` doc vs list

Doc: "Models that do not factorize (rls, kalman, ftrl) report 0". The
`0` arm also covers `ew_cov` (`mahal` and `partial_corr` solve),
`kalman` (inverts the innovation covariance) and others; and see S11 for
`lasso`, which is in the counting arm and never counts. Either count
their failures or say "models that do not count them".

### S9. Kalman: a zero-weight row with a present target skips the per-target decay

`kalman.rs`, `step`. Pattern C. The `None` arm decays `wj` and `wsig`;
the `weight <= 0.0 { continue }` arm, reached with a present target,
decays neither (the standardizer's `n_eff` does decay, through
`stats.update(.., lam, 0)`). `EwRidge` decays both on that row.
Chunk-invariant, and `wj` only gates `> 0`, but `wsig`'s memory grows by
every zero-weight row, so `sigma2` -- and through it `q_i` and the
innovation variance -- follows a recursion the docstring does not
describe. Move the decay above the `weight` test. Test:
`null_targets_decay_the_residual_variance_weight_without_adding_to_it`
(ewridge) ported to kalman with weight 0.

### S10. RLS never predicts from `coef_prior` before its first learned row

`rls.rs`, `predict`, the `self.seen` gate. `EwRidge` with `ridge_decay` +
`coef_prior` -- the mode `agrees_with_ewridge_solved_every_row` says is
the same model -- predicts from the prior as soon as `min_periods`
allows; RLS returns NaN until a row has been learned, whatever the prior.
The warm start ("begin at yesterday's fit") is the stated purpose of
`coef_prior`. Drop the gate when a prior is set, or document the
difference beside the agreement test. Minor beside it: `#[serde(try_from
= "RlsV2")]` cannot fail, and the name reads as if a migration exists;
lib.rs's schema-2 note ("schema-1 rls states are converted on load") is
history now that `MIN_SCHEMA_VERSION` is 6 -- mark it so.

### S11. `Lasso::solve_failures` is never written

`lasso.rs`: the field is `pub`, `AnyModel::solve_failures` reports it,
and nothing increments it. Coordinate descent that leaves `max_cd_iters`
without meeting `cd_tol` is the failure this model has; count it.

### S12. `atomic.rs`: Windows and durability caveats missing

`crates/online-polars/src/atomic.rs`. The module doc says the rename
replaces "on both target platforms". On Windows `MoveFileExW` over a
destination another process holds open **without** `FILE_SHARE_DELETE`
fails with a sharing violation: a Python `open(path, "rb")`, a viewer, an
indexer. Rust's own `File` opens with share-delete, so the two-writer
test passes and says nothing about this. Say it, and consider a retry.
Two smaller ones: the parent directory is not fsynced after the rename,
so the rename itself is not durable on POSIX (inside the "old or new"
contract, but worth a sentence); a kill between `create` and `commit`
leaves `.name.tmpPID-seq` behind and nothing sweeps it on the next run.

### S13. Robust: two asymmetries in `step` and `solve`

`crates/online-core/src/robust.rs`. Pattern C for the first.

- In `step`, the `None` arm decays `cov`, `wj` **and** `wsig`; the
  `w.is_nan() || w <= 0.0` arm (a zero weight, or a NaN robust weight)
  decays `cov` and `wj` and **not** `wsig`. S9's effect, in the model
  whose weights depend most on `sigma2`.
- In `solve`, the unstandardized path counts a total failure
  (`None => self.solve_failures += 1`); the standardized path returns
  through `solve_spd(..)?` before its increment, so a singular
  standardized solve keeps the previous fit *and* reports nothing.
  `a_solve_failure_is_counted_and_the_previous_fit_is_kept` runs with
  `standardize = false`; run it with `true` as well.

### S14. `ew_class` reports the whole-history `n_eff` under a `window`

`ewclass.rs`: `n_eff()` and the `min_periods` gate in `score` read
`self.n_eff`, the live weight, while every class weight, mean and (after
C12) covariance the row is scored on is windowed. Pattern D, the
`ew_class` instance; the snapshot already carries `n_eff * lam`, so the
windowed number is one subtraction away. Decide with C9.

### P1. A windowed `ewridge` allocates an O(k²) view on every row

`ewridge.rs`: `predict` calls `n_eff()`, which calls `view()`, which
clones the `k × k` accumulator through `truncated` and builds per-target
vectors -- on every row, and again in `solve()`. `model.rs` states "no
allocation in the hot path after warmup" as an invariant of `step`. Keep
the truncated weight as one scalar for `n_eff`/`predict` and build the
full view only at solve time. **`lasso.rs` is worse**: `view()` is called
inside the per-target selection loop of `step`, `m` times a row.
`ew_class` computes it once per `score`, which is the right cadence for
its use, but also once more in `class_weights()`.

### P2. `Instance::reset` builds every halflife instance to keep one

`stream.rs`: `build_models(spec).swap_remove(self.mi)`. A five-halflife
grid under `drift_action = "reset"` builds five models per reset per
instance. Add a `build_one_at(spec, mi)`.

### D1. Hard rule 5 vs `MIN_SCHEMA_VERSION = 6`

`lib.rs` documents the 2026-09-07 exception well; `CLAUDE.md` hard rule 5
still reads as unconditional. Put the one-line caveat there too.

### D2. `solve_spd` and `SpdFactor::of` are the same jitter ladder twice

`solve.rs`. Identical today; a future edit to one is a divergence. Write
`solve_spd` as `SpdFactor::of(a, k)` plus a solve.

### D3. `Kalman::coefficients` unscales with the current stats

`kalman.rs`. The betas live in the standardized coordinates of the stats
at the time they were learned; `coefficients()` reads them out with
today's scales and means. The tests acknowledge it ("locking its betas
into the standardized space of the first few rows") and route around it;
the method doc does not say it. `pred` and `coef` are consistent with
each other (both use the current stats), but "coefficient per unit of
`x`" drifts with the standardizer. One paragraph on the method.

### D4. Robust's scale is the plain EW residual variance

`robust.rs`: `s` in the Huber cut and the quantile floor is
`sqrt(sig2)`, the EW mean of squared raw residuals -- which the outliers
Huber exists to resist inflate. The usual choice is a robust scale (MAD
or a Huber-weighted variance). Not a bug; the module doc should say the
scale is not itself robust, since `huber_delta` is "in units of the EW
residual std" and a user will read that as a robust std.
