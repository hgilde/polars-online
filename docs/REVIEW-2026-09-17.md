# Review 2026-09-17 — the changes since 0.6.0

**Scope.** `933ff24..7f08994`, thirteen commits: the runner leaving Python
(task 83), the bank taking a plan (84), the expression plugin removed (85), the
bank on Arrow in four increments (86), the 0.7.0 release, and two
documentation passes removing the plugin's residue.

**Status.** Every finding in §1-§3 was applied in commit `b9e4977` (the first
pass) or the commit that adds this paragraph (the second pass, §5), each
reproduced before its fix and pinned by a test after it. The one exception is
A2, the Python input direction, which is recorded rather than changed: it is
blocked on an ownership step in the C data interface that needs prototyping,
not a fix. §6 records a usage report that arrived during the second pass and
what was done about it.

**Method.** Every finding below was reproduced before it was listed, by running
the code rather than reading it. Three candidates did not survive that and are
recorded in §4 as checked and not found, one of them a performance claim that
a measurement refuted. Each finding carries a reproduction and a concrete
fix. Severity is by consequence: *silent wrong output* > *undocumented
behaviour change* > *lost guard* > *misleading message* > *cosmetic*.

## 1. Bugs

### B1. An Arrow caller who omits a column from `names` gets it silently treated as absent — *silent wrong output*

**Where.** `crates/online-polars/src/arrow.rs`, `ArrowChunk::new` (checks each
column's length against `height` and nothing else) and `ArrowChunk::has`
(reads `names`, not `cols`). `bank.rs` `extract` decides a scoring call's
optional columns with `optional = |name| scoring && !chunk.has(name)`.

**Consequence.** A pure-Arrow caller building a chunk by hand who supplies a
target column in `cols` but forgets to list it in `names` gets a `predict`
that silently treats the target as missing: `resid` and the standardized
residual come back null for every row, with no error. The data was there.

**Reproduce** (Rust integration test; this ran and printed
`has("y") = false although the column is present`):

```rust
use online_polars::{ArrowChunk, ArrowCol, Float64Array};
use polars::prelude::*;
let y = Float64Array::from_iter([Some(1.0)]);
let cols: Vec<(PlSmallStr, ArrowCol)> = vec![("y".into(), ArrowCol::F64(y))];
let chunk = ArrowChunk::new(1, cols, vec![]).unwrap();   // names omits "y"
assert!(chunk.has("y"));                                 // fails today
```

**Fix.** Validate in `ArrowChunk::new` that every column given is listed:

```rust
if let Some((name, _)) = cols.iter().find(|(n, _)| !names.iter().any(|m| m == n)) {
    polars_bail!(ColumnNotFound:
        "column {:?} is given but is not in `names`; every column in `cols` must be listed",
        name.as_str());
}
```

Then add the assertion above to `crates/online-polars/tests/arrow_chunk.rs` as
`a_column_given_but_unlisted_is_refused`. `chunk_from_frame` already lists every
frame column, so the polars path is unaffected.

### B2. Duplicate column names are accepted and the first wins silently — *silent wrong output*

**Where.** `arrow.rs`, `ArrowChunk::new` and `ArrowChunk::find`, which returns
the first `(name, form)` match.

**Consequence.** Two `F64` columns both named `x0` are accepted; every read of
`x0` gets the first. A caller assembling a chunk from two sources with an
overlapping name gets a fit on the wrong column and no error. A name *may*
legitimately appear twice in different forms (a column read as a feature by one
spec and as a group key by another), so the invariant is uniqueness of
`(name, form)`, not of `name`.

**Reproduce** (ran; printed `new() is_ok = true` and
`f64("x0") returned the FIRST column silently: [1.0, 2.0]`):

```rust
let cols: Vec<(PlSmallStr, ArrowCol)> = vec![
    ("x0".into(), ArrowCol::F64(Float64Array::from_iter([Some(1.0), Some(2.0)]))),
    ("x0".into(), ArrowCol::F64(Float64Array::from_iter([Some(9.0), Some(9.0)]))),
];
assert!(ArrowChunk::new(2, cols, vec!["x0".into()]).is_err());   // fails today
```

**Fix.** In `ArrowChunk::new`, refuse a repeated `(name, form)`:

```rust
fn form(c: &ArrowCol) -> &'static str {
    match c { ArrowCol::F64(_) => "number", ArrowCol::Str(_) => "text",
              ArrowCol::I64(_) | ArrowCol::U64(_) => "integer key" }
}
let mut seen = PlHashSet::<(&str, &'static str)>::default();
for (name, col) in &cols {
    if !seen.insert((name.as_str(), form(col))) {
        polars_bail!(Duplicate: "column {:?} is given twice as {}", name.as_str(), form(col));
    }
}
```

Test to add beside B1's: `a_name_given_twice_in_one_form_is_refused`, and its
counterpart `a_name_may_appear_as_number_and_as_key`, which must stay accepted.

### B3. A column supplied in the wrong form is reported as "not found" while the message lists it as present — *misleading message*

**Where.** `arrow.rs`, `ArrowChunk::missing`, used by `f64`, `str` and `key`.

**Consequence.** An Arrow caller who passes the clock as `Int64Array` (a
natural thing to do with a tick counter) reads:

```
not found: spec "m": clock column "t" not found; the frame has columns ["t", "x0", "y"]
```

The message names `t` as both missing and present, and says "the frame" to a
caller who has no frame. The real fault — the column is there in the wrong
form — is not stated, so the caller has nothing to act on.

**Reproduce** (ran; the text above is verbatim):

```rust
let t = Int64Array::from_iter([Some(1i64), Some(2)]);
let cols = vec![("t".into(), ArrowCol::I64(t)),
                ("x0".into(), ArrowCol::F64(f64s(&[1.0, 2.0]))),
                ("y".into(),  ArrowCol::F64(f64s(&[1.0, 2.0])))];
let chunk = ArrowChunk::new(2, cols, names(&["t", "x0", "y"])).unwrap();
let err = Bank::new(vec![spec()]).unwrap().fit_predict_arrow(&chunk).unwrap_err();
assert!(err.to_string().contains("given as an integer key"));   // fails today
```

**Fix.** Give `missing` the form the caller wanted, and check `cols` before
declaring the name absent:

```rust
fn missing(&self, spec: &Spec, role: &str, name: &str, wanted: &str) -> PolarsError {
    if let Some((_, c)) = self.cols.iter().find(|(n, _)| n == name) {
        return polars_err!(SchemaMismatch:
            "spec {:?}: {} column {:?} is given as {}, but a {} is read as {}",
            spec.name, role, name, form(c), role, wanted);
    }
    let have: Vec<&str> = self.names.iter().map(|n| n.as_str()).collect();
    polars_err!(ColumnNotFound:
        "spec {:?}: {} column {:?} not found; the input has columns {:?}",
        spec.name, role, name, have)
}
```

with `f64` passing `"a number"`, `str` passing `"text"`, and `key` passing
`"text or an integer key"`. The polars path never hits the first branch, because
`chunk_from_frame` casts to the wanted form. The not-found branch says "input",
not "frame", since the same message serves an Arrow caller who has a chunk
(this is A5); `tests/test_error_messages.py`'s pin is updated to match.

### B4. `predict` now refuses an unorderable `group_close = "monotone"` key — *undocumented behaviour change*

**Where.** The refusal moved from `bank.rs` `group_key_is_integer`, which the
old code called only from `fit_predict_on_pool` (`933ff24:bank.rs:2720`; the
old `predict_on_pool` at `:2964` never called it), into
`arrow.rs` `chunk_from_frame`, which both `fit_predict` and `predict` now run.

**Consequence.** Before 0.7.0, `predict` on a spec with a monotone close and a
float group column ran (it does not close groups, so it never needed the
order). Now it raises. The new behaviour is arguably right — such a spec cannot
order that dtype whatever the call — but it is a change to a public method with
no changelog line and no test asserting either behaviour.

**Reproduce** (ran; both calls now raise the same `ValueError`):

```python
mono = po.spec.ewridge("m", targets=["y"], features=["x0"], clock="t", halflife=60.0,
                       max_dclock=30.0, group="g", group_close="monotone", min_periods=2.0)
dff = df.with_columns(g=pl.col("t") * 1.5)           # float key
po.ModelBank([mono]).predict(dff)                    # 0.6.0: runs; 0.7.0: ValueError
```

**Fix.** Keep the refusal (consistency beats the old leniency) and make it
deliberate: a test in `tests/test_closed_groups.py`,
`test_predict_refuses_a_key_monotone_cannot_order`, asserting the `ValueError`
and its message on `predict` as well as `fit_predict`; and a line under
`[0.7.0] Changed` in `CHANGELOG.md`. If the old leniency is wanted instead,
`chunk_from_frame` takes a `for_fit: bool` and skips the block when false —
but then the same test asserts that `predict` runs.

### B5. `fit_predict_batches` validates `chunk_rows` for a `DataFrame`, then ignores it — *documented but inconsistent*

**Where.** `python/polars_online/_bank.py`, `fit_predict_batches` (validates
`chunk_rows >= 1`) and `_chunks` (returns `[batches]` for a `DataFrame`
regardless).

**Consequence.** `bank.fit_predict_batches(df, chunk_rows=10)` on a 10M-row
frame feeds one 10M-row chunk. The docstring does say "A `DataFrame` is one
chunk", so this is not silent — but a parameter that is validated and then
discarded is a trap, and the caller who passed it wanted bounded memory.

**Reproduce** (ran; printed `1`):

```python
len(list(po.ModelBank([spec]).fit_predict_batches(df, chunk_rows=10)))   # 120 rows -> 1, not 12
```

**Fix.** Slice the frame when a size is given; `iter_slices` is zero-copy:

```python
if isinstance(batches, pl.DataFrame):
    if chunk_rows is None:
        return [batches]
    return batches.iter_slices(n_rows=chunk_rows)
```

and update the docstring sentence to "A `DataFrame` is fed as one chunk, or in
`chunk_rows` slices when that is given." Test: on 120 rows with
`chunk_rows=10`, twelve frames come out and `save_bytes()` equals the
`LazyFrame` route's, byte for byte.

### B6. The stub-drift test cannot see a mistyped dunder — *lost guard, introduced in `1731325`*

**Where.** `tests/test_kwargs_typing.py`,
`test_the_native_stub_names_the_built_module`. My change to accommodate a
declared `__arrow_c_array__` strips underscore-prefixed names from the stub
side as well as the `dir()` side, so a dunder the stub declares is never
compared to the class.

**Consequence.** A stub that declares `__arrow_c_arry__` (typo) passes. The
stub is what a type checker sees, so the misspelling would tell every
`mypy` user that the real protocol method does not exist.

**Reproduce** (ran, as a replica of the test's logic against a stub string
containing the typo; printed `methods == want -> True`):

```python
import ast
from polars_online import _polars_online as native
stub = "class ArrowStruct:\n    @property\n    def name(self) -> str: ...\n    def __arrow_c_arry__(self, requested_schema=None): ...\n"
cls = [n for n in ast.parse(stub).body if isinstance(n, ast.ClassDef)][0]
methods = {n.name for n in cls.body if isinstance(n, ast.FunctionDef) and not n.name.startswith("_")}
want = {n for n in dir(native.ArrowStruct) if not n.startswith("_")}
assert methods == want          # passes -- the typo is invisible
```

**Fix.** Keep the public-name equality and add a subset check for the dunders
the stub does declare:

```python
declared = {n.name for n in cls.body if isinstance(n, ast.FunctionDef)}
public, dunders = {n for n in declared if not n.startswith("_")}, {n for n in declared if n.startswith("__") and n != "__init__"}
assert public == want, name
assert dunders <= set(dir(getattr(native, name))), f"{name}: stub declares {dunders - set(dir(getattr(native, name)))} which the class has not got"
```

### T1. The tiny-groups memory guard went with the plugin — *lost guard*

**What was lost.** `tests/test_ffi_memory.py::test_plugin_over_groups` fed
1,500 rows over 50 groups through `.over("g")` inside the RSS harness. It is
the test that caught the `PAR_MIN_ROWS` fan-out wobble (`docs/PERFORMANCE.md`,
"The row floor": +4.6 KB/iter against ±2). Task 85 deleted it with the plugin.
No remaining test in that file feeds many small groups; `grep -n "group\|over("
tests/test_ffi_memory.py` finds only a comment.

**Consequence.** A regression in the per-call allocator behaviour for small
groups — the exact class the floor exists to prevent — would now reach `main`
unseen. `crates/online-polars/tests/chunk_plan.rs` checks `PAR_MIN_ROWS` for
*correctness* at the boundary, not for memory.

**Reproduce.** The absence: `grep -n "over(\|groups" tests/test_ffi_memory.py`.

**Fix.** Re-create the workload through the bank's own group column, in the
same harness and against the same per-iteration line the file already uses:

```python
def test_many_tiny_groups(self):

    df = pl.DataFrame({"g": [f"g{i % g}" for i in range(n)],
                       "x0": rng.standard_normal(n), "y": rng.standard_normal(n)})

    self.assert_flat(lambda: po.ModelBank([spec]).fit_predict(df))   # the file's RSS helper
```

## 3. Architecture

### A1. The polars-free API takes a polars type

`ArrowChunk::new(height, cols: Vec<(PlSmallStr, ArrowCol)>, names: Vec<PlSmallStr>)`.
`PlSmallStr` is `polars-utils`', so "a caller holding Arrow arrays can build one
and feed the bank without polars in the process" is true of the engine and
false of the string type. `polars-utils` is a small crate, and the cost is
ergonomic rather than linkage — but the crate's own re-export list was written
so that "feeding the bank as Arrow needs no polars crate of the caller's own",
and this contradicts it. **Fix:** accept `impl Into<PlSmallStr>` for both
parameters, or `&str` slices converted inside `new`; re-export `PlSmallStr` for
the caller who wants to hold one. One-line signature change, no behaviour change.

### A2. The Arrow option is output-only, and the obstacle is recorded

`ModelBank.fit_predict_arrow` still takes a `PyDataFrame`, so a call rides on
pyo3-polars' private boundary on the way in and the public capsule interface
on the way out. This is documented in the README, CLAUDE.md rule 13 and
`docs/PLAN.md` task 86, where the reason is also recorded: the C data interface
requires the consumer to null the producer's `release` pointer, and
polars-arrow keeps `ArrowArray`'s fields `pub(super)`, so a consumer outside
that module cannot mark the source released without writing a zeroed struct
through a raw pointer. It is listed here because a reader of the API alone
would expect symmetry. Nothing to fix without prototyping that ownership step.

### A3. `F64Column::validity` consumes `bits`, so finisher order is load-bearing

`column.rs:118` `validity(&mut self)` does `std::mem::take(&mut self.bits)`
when packed; `is_valid(i)` reads `bits`. `finish_bool_array` computes its
values before calling `validity` and says so in a comment. Today no finisher
calls `is_valid` after `validity`, so nothing is wrong — but the invariant is
enforced by a comment, and a finisher that did the natural thing (validity
first, then a loop over `is_valid`) would silently mask every row as valid.
**Fix:** make `validity` non-consuming — clone `bits` into the `MutableBitmap`
(a `Vec<u8>` clone, one byte per eight rows) — or add
`debug_assert!(!self.packed || !self.bits.is_empty(), "validity() already taken")`
at the top of `is_valid`. The first removes the trap; the second makes it
loud.

### A4. `ArrowStruct.__arrow_c_array__` takes `&mut self`

Two threads exporting the same struct at once get pyo3's generic
`RuntimeError: Already borrowed`, where every `ModelBank` method takes its
borrow through `busy()` and names itself. Harmless (the second caller would
have got the "already exported" `ValueError` a moment later anyway), but the
one method in the module that does not follow the file's own convention.
**Fix:** `fn __arrow_c_array__(slf: &Bound<'_, Self>, ...)` with
`slf.try_borrow_mut().map_err(|_| busy("ArrowStruct.__arrow_c_array__"))?`.

### A5. The error vocabulary says "frame" to callers who have none

`ArrowChunk::missing` says "the frame has columns"; B3's fix changes it to
"the chunk". `ArrowChunk::new`'s length error says "the chunk has" already.
Cosmetic, folded into B3.

### A6. README line 10 counts interfaces ambiguously since the plugin left

"Two of the three ways this library plugs into Polars carry no stability
promise" was written when the three were the plugin, `ModelBank` and the IO
plugin. Now the two ways *into Polars* both carry no promise, and the third
way is Arrow's, not Polars'. The sentence is not false but no longer says what
it means. **Fix:** "Both of the ways this library plugs into Polars carry no
stability promise from Polars, so `polars>=1.34.0,<3` is measured rather than
guaranteed …" — and let the "Which interfaces carry a promise" section, which
already explains the third, carry the rest.

## 4. Checked, and not a finding

Recorded so the next reader does not re-derive them.

- **Multi-chunk input is not slower.** I expected `chunk_from_frame`'s
  `rechunk()` plus `f64_column`'s `into_owned()` to add a copy over the old
  `materialized` path for a multi-chunk target, clock or weight column.
  Measured on 1M rows × 5 columns, best of three: **one chunk 112 ms, eight
  chunks 104 ms, ratio 0.93.** Within noise, and if anything the other way.
  The extra copy is real in the code but not in the clock; not worth a change.
- **The closed-groups sidecar is written on error by `fit_predict_batches` and
  not by the plan.** `_bank.py` `_feed` writes in a `finally`; `_frame.py`
  `_source` comments "Not in a `finally`" deliberately. Both are right for
  their semantics: the plan form discards a fresh bank on error, so nothing is
  lost and purity holds; the batches form feeds a bank the caller keeps and
  has already drained, so the file is the only place those groups now are.
- **No runner code path lost its tests.** `tests/test_runner.py` (486 lines)
  went with the Python runner. The Rust runner the CLI uses is covered by
  `crates/online-polars/tests/runner.rs` for every format (Parquet ×12, Ndjson
  ×5, Csv ×4, Ipc ×4, JsonLines, and `Format::ALL` sweeps), and the CLI itself
  by `run_online` in five Python files. The deleted tests covered Python-side
  *sources* (`LazyFrame`, `DataFrame`, list, generator) that no longer exist.
- **`fit()` is byte-identical to `fit_predict_batches`.**
  `tests/test_bank_ergonomics.py:265-266` asserts `quiet.save_bytes() ==
  kept.save_bytes()`.
- **`docs/VALIDATION.md`'s hand-edited version line is verified.** The
  `pins`-marked test regenerates and compares the whole document; the intraday
  cache is present and the last gate's only skips were unrelated, so it ran.
- **A spec named like an input column is refused through the Arrow path.**
  `refuse_name_clash` reads `chunk.names()`; ran, raises the `Duplicate` error.
- **The shell-block harness runs each line separately.** A backslash
  continuation or a `cd` in `docs/RUNNER.md`'s blocks would break; there is
  none today. Latent only.
- **The polars-path error messages are unchanged.** The eight suites that
  assert on relocated messages (391 tests) pass; the temporal-clock and
  monotone refusals moved earlier in the call but kept their text.

## 5. Second pass — the first pass's own fixes, and what they missed

The fix commit `b9e4977` had been reviewed by nobody, so it was read with the
same eye as the original diff. Everything here is applied in the commit that
adds this section.

### S1. `ArrowStruct` was not nameable from the package, nor in the reference

**Reproduce.** `python -c "import polars_online as po; po.ArrowStruct"` raised
`AttributeError`; `grep ArrowStruct docs/reference/*.rst` found nothing. A
public method returned a type a caller could neither annotate with nor read
about. **Fix.** Exported as `polars_online.ArrowStruct`, `autoclass`'d in
`docs/reference/polars_online.rst`, and `_bank.py` annotates with it; the API
snapshot gains the name.

### S2. Nine of twelve Arrow tests bypassed the public wrapper

**Reproduce.** `grep -c "_native.fit_predict_arrow" tests/test_arrow_capsule.py`
gave 9 against 3 through `ModelBank.fit_predict_arrow` -- so `_check_frame`
and the wrapper's own body were exercised by three tests. **Fix.** All go
through the public method; a new test pins the `TypeError` for a `LazyFrame`
on both Arrow methods by name.

### S3. A broken bank was cast before it was refused

**Reproduce.** `bank.rs`: `fit_predict` called `chunk_from_frame` and only then,
inside the pool, `refuse_if_broken` -- so a bank that could not go on did a
frame's worth of casting first, and with a bad column reported the column
rather than its own state. The one test pinning the refusal
(`tests/test_window_budget.py:67`) feeds a valid frame, so the precedence was
unpinned. **Fix.** `refuse_if_broken` first, in both polars entry points; the
Arrow pair keep theirs inside the pool. Precedence against a bad column stays
untested: constructing a broken bank needs a refusing `window_budget`, and the
reorder is a pure swap.

### S4. `named_columns` truncated silently on a length mismatch

**Fix.** `debug_assert_eq!(specs.len(), arrays.len())`; the invariant is
internal and now loud in test builds.

### S5. The adapter's duplicate check cast a column twice to drop one

**Reproduce.** `ROUNDTRIP_SPECS` in `tests/test_bank_ergonomics.py` reads `g`
as a group key and as a session; both cast to text, and the first-pass dedup
performed the second cast before discarding it. **Fix.** `form_of(want, dtype)`
predicts the form a role will produce, so the second role is skipped before
its cast.

### S6. Recorded from the first pass: the strict check broke the adapter

## 6. A usage report: an unordered join under the streaming engine

**The report.** "`fit(lf)` runs the plan through the streaming engine, so a
plan with an unordered join silently delivers a different stream than
`lf.collect()` would."

**Reproduced, and it is worse than "different".** 200,000 rows joined to a
1,000-row dimension without `maintain_order`: `collect()` returned the rows
**in input order**; `collect_batches(maintain_order=True)` did not; the two
disagreed. With `maintain_order="left"` both agreed and both kept input order.
So a plan a user validates by collecting it looks ordered and then learns
something else when fed -- and an online model's row order *is* the model.

**Detection.** Yes, and it is implemented. `LazyFrame.serialize(format="json")`
gives the DSL plan as externally tagged JSON; the shape was read from
`polars-plan`'s source and confirmed empirically: `Join.options.args.maintain_order`
is `"None"`/`"Left"`/… (PascalCase -- serde has no `rename_all` there, strum
does), `GroupBy.maintain_order` and `Distinct.options.maintain_order` are
booleans. `explain()` was checked and rejected: its formatter prints
`{how} JOIN:` with no `maintain_order`, so it cannot tell the two joins apart.
The walker flags a join with `"None"`, a `group_by` with `false`, and *every*
`unique` -- polars' own note on `DistinctOptionsDSL` says its flag is not
supported in the streaming engine -- and stops at a `Sort`, which settles the
order of everything beneath it; a join keeping one side's order is followed on
that side alone.

**Three constraints, stated rather than hidden.** The json format is
deprecated in this polars and issues a `UserWarning`, which is suppressed
around the one call so the caller never sees it. A plan already holding one
of our own IO sources cannot be serialized (it needs `cloudpickle`), so the
inspection swallows every exception and says nothing; a test pins that a
bank still runs on such a plan. When polars removes the format, the detector
falls silent -- the docs line on each entry point is the guarantee, the
warning is the net under it.

**Fix.** `OrderNotGuaranteedWarning`, a `UserWarning` (shown by default where a
`DeprecationWarning` is hidden), raised by `ModelBank.fit`,
`fit_predict_batches`, `lf.online.fit_predict` and `lf.online.predict` -- the
plan forms at build time, before a row moves -- naming the entry point, each
node, and the fix. The `stacklevel` walks to the first frame outside the
package so the warning lands on the caller's line. Docs lines on all four
entry points and under the README's "Two guarantees", which both rest on a
fixed order. `tests/test_order_hazards.py` holds all of it: each node kind,
each entry point, the sort-above/sort-below cases, that a frame or an iterator
is not inspected, that polars' deprecation does not leak, silence when the
plan cannot be read, and the warning's category and attribution.
