### B1. A backwards clock on a session change bypasses `on_clock_reset` — *lost guard*

**Reachability, from the bank read (2026-09-18): probably → §3.** `Spec::clock_cfg`
(`spec.rs:1776-1782`) requires `session_gap` whenever `session` is given, *except* under
`group_close = "session"`. So the only `ClockCfg` with a session column and
`session_gap: None` that the bank ever builds is a closing spec's — and there `process`
(`bank.rs:762-768`) splits the run at every session boundary and recreates the stream,
so the rows after the boundary never compare their clock with the rows before it.
`check_clock` (`bank.rs:2766-2777`) does run over the *whole* run on the old stream, so
an `Error` policy firing at the boundary would be a spurious refusal; the clamp is the
right answer for the one caller that reaches it. A direct `online-core` user can still
build the config, so the fix is a doc comment on `ClockState` (and perhaps a
`debug_assert`), not a behaviour change. Confirm against `clock.rs:207-247` and PLAN §3
in phase 2 before moving it.

**Where.** `crates/online-core/src/clock.rs:207-247`, `ClockState::advance`.
**Claim.** When `session_changed` and `cfg.session_gap` is `None`, the delta is
`raw.clamp(0.0, max_dclock)`: a negative raw delta becomes 0 silently. The `raw < 0.0`
arm that consults `on_clock_reset` (`Max` / `Zero` / `ResetState` / `Error`) is reached
only when the session did *not* change. So `on_clock_reset = "error"` — whose stated
purpose (line 59) is to make a mis-sorted chunk loud — never fires on a row whose
session id also changed, and `reset_state` never resets there.
**Evidence.** `if session_changed { match cfg.session_gap { …, None => { capped = raw >
cfg.max_dclock; raw.clamp(0.0, cfg.max_dclock) } } } else if raw < 0.0 { match
cfg.on_clock_reset { … } }`. The test `session_gap_overrides_delta` covers `Gap(7.5)`
("session gap wins") and `Reset`, never `None`.
**Consequence.** Interleaved or mis-sorted rows that happen to change session are
absorbed as a zero delta under every policy, including the one chosen to refuse them.
**Fix / test.** With `session_gap: None` a session change is an ordinary row for the
clock: fall through to the `raw < 0.0` policy. Test: `Error` policy, sessions 1 → 2 with
clock 10 → 4, expect `backwards == Some(-6.0)`; `ResetState` expects `reset`. Read PLAN
§3 for what is promised before changing.
**Status.** candidate.

### S1. The sign hit rate does not age on an excluded `y = 0` row — *inconsistent, low*

**Where.** `crates/online-core/src/stats.rs:283-313`, `SlotMetrics::update`.
**Claim.** A row skipped for a non-finite `pred`/`y` or `w <= 0` ages every estimate
(`joint.decay(lam)`, `hit_w *= lam`, lines 288-289). A finite row with `y == 0` under
`binary = false` is scored into `ic`/`r2` (`joint.update`, `mse`) but the hit-rate
branch (`if binary || y != 0.0`) is skipped whole, so `hits`/`hit_w` are neither scored
nor decayed. The hit rate then runs on a different clock from `ic` and `r2` whenever the
target is exactly zero (discrete or rounded targets).
**Fix / test.** `else { self.hit_w *= lam; }` on the excluded path. Test: 100 rows of
`(0.9, 1.0)` then 100 of `(0.9, 0.0)` at `lam = 0.9`: `hit_w` must shrink by `0.9^100`.
**Status.** candidate (low). Changes `hit_rate` only on streams with exact zeros — the
user's call.

### D1. `EwAutoCorr::get` reports `Some(0.0)` before any lagged pair when `lag ≥ 2` — *doc vs code, low*

### B2. `coef_prior` is ignored by the standardized solve through the origin — *silent wrong output*

**Where.** `crates/online-core/src/ewridge.rs:742-752` (the call) and `804-844`
(`solve_scaled_through_origin`).
**Claim.** `solve` has four branches. `ridge_decay` adds `ps·ridge·c0` to the right-hand

### S3. `corrchange`'s delta-method gradient has the wrong powers of σ, so the monitor statistic depends on the data's units — *silent wrong output*

**Where.** `crates/online-core/src/corrchange.rs:386-391`, `long_run_sd`, the `d3`
array; the same expression in the test `the_statistic_is_its_definition` (864-868).
**Claim.** `ρ = σ_xy·(σ_x²)^{-1/2}·(σ_y²)^{-1/2}`, so the gradient with respect to
`(σ_x², σ_y², σ_xy)` is `(−½·σ_xy/(σ_x³·σ_y), −½·σ_xy/(σ_x·σ_y³), 1/(σ_x·σ_y))`.
The code has `−0.5·sxy·sy/(sx·sx·sx)` and `−0.5·sxy·sx/(sy·sy·sy)`: the first entry is
multiplied by `σ_y²`, the second by `σ_x²`. Units: `∂ρ/∂σ_x²` must be `1/x²`; the code's
is `y²/x²`. Only at `σ_x = σ_y = 1` do the two coincide.
**Evidence.** Under `y → c·y`, `σ_xy → c·σ_xy`, `σ_y → c·σ_y`: the correct entry is
unchanged (ρ is scale-free), the code's scales by `c²`, and its contribution to `D̂²`
(`f·Σ̂·f'`, with `Σ̂₀₀` the long-run variance of `x²`, unchanged by `y`'s scale) by `c⁴`.
So `Q = max_j (j/√T)|ρ̂_j − ρ̂_T|/D̂` moves with the units of `y`, which a correlation
test cannot do. Every test feeds `Normals::pair` — unit variance both sides — so the
paper's size and power tables are reproduced exactly where the defect vanishes; the
"definition" test carries the same formula.
**Consequence.** On returns in basis points against returns in percent (`σ` ratio 100),
`D̂` is wrong by orders of magnitude and the monitor flags nothing or everything, with
no error. Users on unit-scale data are unaffected.
**Fix / test.** `d3 = [-0.5*sxy/(sx*sx*sx*sy), -0.5*sxy/(sx*sy*sy*sy), 1.0/(sx*sy)]`.
Tests: (1) invariance — the same stream with `y` multiplied by 100 must give `Q` equal
to `1e-9`; fails today. (2) the gradient against a central finite difference of
`corr_of` in each of the three moments. (3) keep the size test but on
`(x, 100·y)`. Also fix the longhand in the existing test, which mirrors the bug.
**Status.** reproduced 2026-09-19 (batch 1); fixed in batch 1.

### T4. `test_constraints.py` seeds its oracle streams from `hash()` — *non-reproducible test, low*

`tests/test_constraints.py:414` and `:453`: `seed=hash((which, schedule)) % 1000` and
`seed=hash((which, mode)) % 1000`. `str.__hash__` is salted per interpreter process

(`list(CONSTRAINTS).index(which) * 3 + SCHEDULES.index(schedule)`) or from
`zlib.crc32(f"{which}/{schedule}".encode())`, which is stable across processes.

### Batch 4 — the four deferred items (done on the user's instruction)

The perf/edge items batch 3 recorded as deferred, now fixed. Two were real
bugs (each reproduced first), two were performance.

- **arrow integer-key ordering (was V12), real bug.** When one integer column
  is both `session` (cast to text) and `group` (a key), `ArrowChunk::key`
  returned the text form, so `group_close = "monotone"` ordered it lexically
  and refused a numerically sorted key at "10 after 9". `key` now prefers the
  integer form. Reproduced by
  `test_closed_groups.py::test_an_integer_key_used_as_both_session_and_group_orders_numerically`
  (raised before, passes after). My batch-3 note that "the fix does not match
  the data model" was wrong: a column *can* be present in two forms, and
  preferring the integer one is the fix.
- **hmm state ageing on a total density failure, real bug.** A row whose
  densities are all non-finite advanced `n_eff` but did not age the states or
  the counts. It now ages them by `lam` and adds nothing, like a zero-weight
  row. Reproduced by
  `hmm.rs::a_row_that_fails_to_score_does_not_advance_n_eff` (a huge finite
  feature overflows the quadratic form; `n_eff` advanced alone before, is
  unchanged after at `lam = 1`).
- **hmm full-covariance factor cache, performance.** The `full` shape
  refactorized every state on every row; it now keeps the `ew_class` `Factors`
  cache, rebuilt from the pre-row state at the top of `step` and dropped
  whenever a state changes, so `learn = false` scoring factorizes each state
  once. Output bit-identical (the hmm golden and the Hamilton-recursion oracle
  both unchanged).
- **refresh group-key clones, performance.** The tick operator cloned the
  group key into both maps on every row; it now updates in place and clones
  only the first row of each group.
